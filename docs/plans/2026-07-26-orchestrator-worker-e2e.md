for _, tool := range allTools {

(`config.go:757-780`) содержит 20 имён и **среди них нет

`ask_question` не встречается в `internal/config/` ни разу.

**Следствие:** инструмент конструируется и тут же выбрасывается фильтром —
**для каждого агента, включая верхнеуровневого кодера**. Модель никогда
его не видит. `exit_reason: "awaiting_answer"` не может возникнуть в
принципе.

**Почему не поймали:** `internal/agent/tools/ask_question_test.go`
тестирует объект инструмента изолированно, `internal/app/run_result_test.go`
— маппинг ошибки в `exit_reason` изолированно. Ни один тест не проходит
через `buildTools`, то есть **проводка не покрыта вообще**. Классический
разрыв: обе половины зелёные, соединения между ними нет.

**Задеты задачи:** #55 (сам инструмент), #56 (чипы в веб-UI — рендерят то,
что никогда не придёт), #57 (документация `/crush` — описывает
несуществующее поведение). Ни одну не надо откатывать — надо починить
проводку, и все три оживут.

### 🔴 BUG-2 — воркер read-only, «делегировать ручную работу» невозможно

`internal/config/config.go:821-829`, конфиг суб-агента `AgentTask`:

```go
AgentTask: {
    ...
    AllowedTools: resolveReadOnlyTools(allowedTools),
    AllowedMCP:   map[string][]string{},

```

а `resolveReadOnlyTools` (`config.go:790-794`) оставляет ровно:

```go

```

**Следствие:** суб-агент (то есть будущий воркер) **не может ни
редактировать файлы, ни писать, ни запускать bash**. Вся конструкция
«Smart — оркестратор, всю ручную работу делают воркеры» **нереализуема на
текущем конфиге**. Задачи #59 (выбор модели воркера) и #60 (инструкция
делегировать) обе исходят из того, что воркер что-то делает руками — а он
физически не может.

Дополнительно: тот же фильтр не пропустит воркеру и `ask_question` (его
нет в read-only списке), так что пункт **C** заблокирован и этим тоже.

### 🟡 GAP-3 — вопрос воркера доедет как «ошибка»

`internal/agent/coordinator.go:2354-2356`, в `runSubAgent`:

```go
if err != nil {
    return fantasy.NewTextErrorResponse(fmt.Sprintf("Failed to generate response: %s", err)), nil
}
```

Любая ошибка суб-агента схлопывается в текстовую ошибку инструмента. Есть
и хорошее: Go-ошибка возвращается `nil`, значит **родительский ход не
падает** — это уже правильно и менять не надо. Но `AwaitingAnswerError`
приедет к оркестратору в виде строки `Failed to generate response: agent
asked a question...`, то есть **как сбой, а не как вопрос**. Модель-родитель
скорее решит, что воркер сломался, и пойдёт переделывать сама — ровно
противоположно задуманному.

### 🟡 GAP-4 — нет возобновления суб-сессии, ответ негде применить

`runSubAgent` всегда создаёт **новую** сессию:
`CreateAgentToolSessionID(params.AgentMessageID, params.ToolCallID)`
(`coordinator.go:2300-2301`). ID детерминирован от пары
(сообщение, tool-call), значит следующий вызов инструмента `agent` — это
всегда **другая** сессия. Возобновить существующую нечем: у инструмента
`agent` один параметр `Prompt` (`internal/agent/agent_tool.go:18-20`).

**Следствие:** даже если оркестратор поймёт вопрос и придумает ответ,
передать его «тому самому» воркеру некуда — весь контекст воркера
потерян, задачу придётся переформулировать и запустить с нуля.

## 3. Почему «без прерывания работы» не может быть синхронным

Разберём физику. Когда воркер работает, родитель-оркестратор **приостановлен
внутри собственного вызова инструмента** `agent` и ждёт возврата из
`runSubAgent`. LLM-родитель в этот момент не «работает» — он не может ничего
решить или ответить, пока не получит результат инструмента.

Значит схема «воркер блокируется → спрашивает родителя → родитель отвечает →
воркер продолжает в том же вызове» — **дедлок по построению**. Родитель
заблокирован на воркере, воркер заблокирован на родителе. Никакой канал это
не спасёт: некому проснуться.

(Ровно этот же вывод уже был сделан в этой сессии для веб-UI — см.
`docs/plans/2026-07-19-upstream-triage-and-question-tool.md`, раздел
«Фаза 3»: блокирующего канала в кодовой базе нет нигде, включая
permissions.)

### Реализуемый дизайн — **«вернуть и возобновить»**

1. Воркер зовёт `ask_question` → `AwaitingAnswerError` → его ход
   останавливается (механизм уже есть).
2. `runSubAgent` **отдельно распознаёт** этот случай и возвращает не
   «ошибку», а **нормальный, корректно оформленный результат инструмента**:
   ```
   SUB-AGENT QUESTION (session <child-id>): <вопрос>
   Suggested options: a | b | c
   The sub-agent is paused with its context intact. To answer, call the
   `agent` tool again with resume_session_id="<child-id>" and your answer
   as the prompt. To abandon it instead, just continue on your own.
   ```
3. **Ход оркестратора не прерывается** — он просто получил результат
   инструмента и продолжает свой ход. ✅ Это и есть «без прерывания работы»
   в реализуемом смысле.
4. Оркестратор решает ответ (сам, или — если это действительно вопрос к
   человеку — эскалирует наружу через свой `ask_question`, пункт **D**) и
   зовёт `agent` с `resume_session_id` → `runSubAgent` **возобновляет ту же
   дочернюю сессию**, воркер продолжает с полным контекстом. ✅ Работа
   воркера не выброшена.

Это честная интерпретация требования. Полностью синхронный вариант
невозможен — и это надо зафиксировать, чтобы не пытаться реализовать его
снова через полгода.

### Двухуровневая эскалация, целиком

```
Claude Code (внешний оркестратор, человек рядом)
   ▲  D: crush run завершается, exit_reason="awaiting_answer",
   │     резюме командой `crush run --session <id> "<ответ>"`   [ПРЕРЫВАЕТ]
   │
Smart-оркестратор (crush run --role smart, worker задан)
   ▲  C: результат инструмента "SUB-AGENT QUESTION", ответ через
   │     agent(resume_session_id=..., prompt=<ответ>)          [НЕ ПРЕРЫВАЕТ]
   │
Worker-суб-агент (agent tool → модель из слота worker)
```

Разница осмысленна: **внутри** одного процесса есть кому ответить
(оркестратор жив и продолжает ход), **наружу** отвечать некому — процесс
обязан завершиться и попросить, чтобы его перезапустили с ответом.

### Фаза 1 — починить проводку (блокирует всё остальное)

**1.1 — BUG-1: зарегистрировать `ask_question`.**
Добавить `"ask_question"` в `allToolNames()` (`internal/config/config.go:757`).
Решить и зафиксировать: попадает ли он в `resolveReadOnlyTools` — **да,
должен**, иначе воркер не сможет спрашивать (пункт C), а вопрос — операция
безусловно безопасная (побочных эффектов нет, только останавливает ход).
Тест: строить `buildTools` для кодера и для task-агента и **проверять
наличие `ask_question` в итоговом наборе** — то есть тест именно на
проводку, которой не хватало.

**1.2 — BUG-2: дать воркеру рабочие руки.**
Суб-агент должен получать полноценный набор инструментов, **когда он
воркер**, сохранив read-only поведение для обычного «поисково-контекстного»
task-агента (интерактивный режим, воркер не задан) — это требование
обратной совместимости «если воркер не задан, работаем по-старому».
Наиболее аккуратно: не трогать `AgentTask` в `SetupAgents`, а выбирать
набор инструментов в момент построения суб-агента
(`coordinator.buildAgent`/`buildTools`), опираясь на тот же признак
«родитель = smart + worker сконфигурирован», что вводит #59
(`SetActiveModelRole`). Набор для воркера: read-only + `edit`, `multiedit`,
`write`, `bash`, `todos`, `download`, `fetch`. **Не давать** `agent` —
воркер не должен плодить под-воркеров (защита от рекурсии).
Тесты: воркер не задан → набор ровно как сегодня (регрессия); воркер задан
и родитель smart → в наборе есть `edit`/`write`/`bash` и нет `agent`.

### Фаза 2 — снять запрет на суб-агентов (пункт A)

`internal/cmd/run.go:459-475`: сейчас и «флаг не передан», и явное
`--agents single` дают `agentsDisable = true`, различить их нельзя.
`internal/app/app.go:844-846` по этому флагу вырезает `agent` и

Надо: различать «по умолчанию» и «оператор явно попросил single», и

`ModelRole == large` (smart), (в) worker сконфигурирован. Явный
`--agents single` уважать всегда — оператор сказал прямо.

Возвращать при обходе **только `agent`**, оставив `agentic_fetch`
выключенным: это отдельная история (веб-фетч, всегда на малой модели), к
делегированию ручной работы отношения не имеет. Консервативнее и уже.

Тесты: таблица из четырёх комбинаций (флаг явный/нет × worker есть/нет) плюс
проверка, что `--role fast` с заданным воркером запрет **не** обходит.

**3.2** — возобновление суб-сессии: добавить в `AgentParams`

Проверять принадлежность: возобновляемая сессия обязана быть **дочерней для

Описание инструмента `agent` (`internal/agent/templates/agent_tool.md`)

Тесты: вопрос воркера превращается в результат-вопрос, а не в ошибку;

### Фаза 4 — смок-тестирование (пункты B, C, E)

Разделяем на два разных инструмента — это принципиально:

**4.1 — автоматические тесты без провайдера** (быстрые, в CI).
Всё, что выше в фазах 1–3, покрывается юнит/интеграционными тестами на
механику: состав инструментов, логика обхода запрета, оформление вопроса,
возобновление сессии. Провайдер не нужен, значит это обычные `go test`,
живут вместе с кодом.

**4.2 — ручной смок-E2E** (пункт B, руками, один раз, с живой моделью).
Автоматизировать полноценный E2E с настоящим провайдером не стоит: дорого,
флаки, и в CI нет ключей. Поэтому — сценарный ручной прогон с фиксацией
результата в отчёте. Сценарии:

- **S1 (базовый, пункт B).** Настроить worker на дешёвую модель, запустить
  `crush run --role smart --json` с задачей, требующей правки файла.
  Проверить: в `tool_calls` есть `agent`; создана дочерняя сессия
  (`crush sessions tree`); файл реально изменён; результат воркера дошёл до
  оркестратора и учтён в финальном ответе; стоимость дочерней сессии
  вкатилась в родительскую (`updateParentSessionCost`).
- **S2 (воркер спрашивает, пункт C).** Задача, сформулированная так, чтобы у
  воркера возникла неоднозначность (например: «поправь конфиг, но какое
  значение таймаута ставить — не сказано»). Проверить: воркер зовёт
  `ask_question`; оркестратор получает результат-**вопрос**, а не ошибку;
  оркестратор отвечает через `resume_session_id`; воркер продолжает **в той
  же** сессии и доводит задачу; **ход оркестратора ни разу не прерывался**

- **S3 (оркестратор спрашивает наружу, пункт D).** Задача, где неоднозначность

  свой `ask_question`; процесс **завершается** с
  `exit_reason: "awaiting_answer"`; в `.error` лежит вопрос и готовая команда
  `crush run --session <id> "<ответ>"`; запуск этой команды продолжает сессию

  починен.**

  суб-агенты по-прежнему выключены в `crush run` по умолчанию, промпт
  оркестратора не содержит блока про делегирование, поведение идентично
  тому, что было до всей этой фичи.

Отчёт по прогонам сложить в `docs/reports/` (или дописать в этот файл
разделом «Результаты смок-прогона»), чтобы следующий раз было с чем

## 6. Что важно не потерять

- **Обратная совместимость — жёсткое требование.** Воркер не задан →
  поведение бит-в-бит прежнее: read-only суб-агент, суб-агенты в `crush run`
  выключены, блока в промпте нет. Каждая фаза обязана иметь тест именно на
  это, а не только на новую ветку.
- **Явный `--agents single` сильнее автообхода.** Оператор сказал прямо —
  уважаем.
- **Воркер не получает инструмент `agent`.** Иначе рекурсивное размножение.
- **Синхронный вопрос воркер↔оркестратор невозможен** (раздел 3). Если
  когда-нибудь снова захочется — перечитать про дедлок, а не изобретать
  канал.
- **`runSubAgent` возвращает `nil` Go-ошибку** для сбоев суб-агента, и это
  правильно: падение воркера не должно ронять ход оркестратора. Оформление
  вопроса добавляется **рядом**, не вместо.
