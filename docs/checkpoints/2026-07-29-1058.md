Go-линкер уже применяет rename-aside как штатный приём при неудачном

## Decisions

- Отброшен per-folder кэш бинарника с self-relaunch (ред. 1) в пользу
  rename-aside на единственном каноническом пути установки — эксперимент
  показал, что это даёт тот же результат (горячая замена, свежая версия
  для новых запусков, папки не блокируют друг друга) без единой лишней
  копии на диск.
- Ключ npm-кэша — `fnv1a64(size + mtime + pkgVersion)`, а не голая
  `pkgVersion`: иначе `deploy.go`-пересборки без смены версии пакета
  молча обслуживались бы устаревшей закэшированной копией.
- Ключ npm-кэша — в имени КАТАЛОГА (`<cache>/<key>/crush.exe`), не в
  имени файла (`crush-<key>.exe`): имя процесса должно остаться
  `crush.exe` ради `agentguard`'s рекурсивного self-block по имени,
  `taskkill /IM`, диспетчера задач.
- Дети процессов, спавненные через `os.Executable()` (`queue.go:332`),
  ПОСЛЕ горячей замены получают текущий канонический (новый) бинарник —
  не version pinning к версии родителя. Это поведение ОС по умолчанию,
  не требует кода/теста, только комментарий — альтернатива (резолвить
  путь один раз при старте) была рассмотрена и отвергнута как логически
  несостоятельная.
- Установленный на машине пользователя пакет — upstream
  `@charmland/crush` с подменённым бинарником, а не форковый
  `@phpcraftdream/crush`. По явному подтверждению пользователя: снести
  upstream полностью, собрать и локально установить форковый пакет
  (0.1.7, ещё не опубликован — в реестре только 0.1.6).
