**Round-10 review verdict**: `c23ef274` closed BLOCKER-1/BLOCKER-2 but
introduced two narrower HIGH-severity follow-up regressions in the fix
itself, both confirmed by direct code read before fixing:

1. **HIGH-1**: `drainOrReleaseMerged`'s legacy-`messageQueue` reclaim path
   called plain `mailbox.submit()`, which — being the only idle→owned
   transition — always bumps the ownership epoch. The bumped epoch was
   discarded; `Run`'s loop kept using its original, now-stale epoch for
   the rest of the call. The next release attempt under that stale epoch
   found a mismatch, assumed a different owner held the session, and did
   nothing — recreating the exact permanent-wedge shape the epoch
   mechanism exists to prevent, via a narrower trigger (a message landing
   in the legacy queue in the gap between a turn's release-to-idle and
   its own check of that queue).
2. **HIGH-2**: `Run`'s cleanup defer (`abandonOwnership`) logged and
   discarded anything still queued when a turn ended on a genuine
   (non-cancel) error — reachable on any ordinary provider/DB error with
   a second message queued concurrently, not just the rare pre-loop
   bail-out. Pre-migration, that message lived in `messageQueue` and was
   picked up by the next `Run()` call; the fix in `c23ef274` turned
   "stranded forever" into "silently lost" instead of "recoverable."

Also flagged (**MEDIUM-1**): the existing
`TestRun_OSLockAcquisitionFailure_DoesNotPermanentlyWedgeMailbox` test's
final assertion (`assert.NoError`) passes vacuously in exactly the
regressed case it claims to catch, since a wedged session silently
queuing and `Run` returning `(nil, nil)` is also `err == nil`.

Fixed in `fa2d2afd`:
- HIGH-1: added `mailbox.reclaimSameEra`, which re-owns the mailbox for
  the SAME era instead of starting a new one via `submit()`.
  `drainOrReleaseMerged` uses it for the legacy-queue reclaim; on the
  (vanishingly rare) case a genuinely different owner claimed a new era
  in that exact gap, the popped item goes back onto the legacy queue
  rather than forcing ownership into a lost race.
- HIGH-2: `Run`'s defer now re-queues anything `abandonOwnership` found
  into `messageQueue` (not epoch-scoped, safe across eras) instead of
  discarding it.
- MEDIUM-1: strengthened the existing test's final assertion to check
  the returned result is non-nil, not just that no error occurred.

**A real bug was caught mid-implementation, not just in review**: the
first version of `reclaimSameEra` also appended the reclaimed call to
`mb.submitted`, duplicating it — the reclaimed turn ran it as its prompt
AND left an identical copy queued, so that turn's own end-of-turn drain
found it "still there" and ran a spurious THIRD turn on the same content.
This was caught by the test suite itself: two pre-existing tests
(`TestRun_QueueDrain_DoesNotDeadlockOnOwnSessionLock`,
`TestRunTurn_ShouldSummarize_QueuedMessageContinuesWithoutLockDeadlock`)
and the new HIGH-1 regression test all started asserting one extra
provider call than expected. Fixed by not queuing at all — matching
`submit()`'s own contract that becoming owner means running the call
directly.
