**1. Per-message token & prompt-cache statistics (`d9a394f6`).** Investigated
how the four providers report usage and found the codebase had TWO mutually
incompatible conventions silently sharing one field. Established each
empirically by running the binaries three times against a fixed prompt and
watching which counter moved: claude's `input_tokens` is EXCLUSIVE of cache,
codex's and gemini's are INCLUSIVE. Three real bugs fell out — codex
double-counted every cached token (23768 reported vs 16856 actual, +41%),
gemini's `cached`/`input` fields were never declared in the parser struct and
were dropped at unmarshal, and `session.PromptTokens` summed only input +
cache-read, omitting cache-WRITE (5842 recorded where the true prompt was
22826, −74%, in the direction that DELAYS auto-summarization and risks
context overruns). The third was introduced by this very work and caught only
because the operator asked "баг исправлен?" and I re-traced the path
end-to-end instead of re-reading the diff.

**2. Statistics by model over periods (`18706ce9`).** New `crush sessions
cache [id] [--since D] [--by model|day] [--json]`, backed by cross-session
sqlc aggregates. Verifying it on seeded data (rather than only the empty
case) exposed that `--since` never filtered at all: `parsePlainInt` used
`fmt.Sscanf("%d")`, which parses leading digits and reports no error for the
remainder, so the "bare integer means days" branch swallowed every duration —
`30m` meant 30 DAYS. Pre-existing, and it also broke `sessions cost --since`,
whose help has advertised Go durations the whole time.

## Decisions

- **Did NOT merge cache columns into `sessions cost`.** It reads session-level
  last-snapshot counters; the cache view reads per-message rows. Adjacent
  columns would imply the two are comparable. Its help now states the caveat
  and points at `sessions cache` instead. Recorded in the plan as "done as a
  documented pointer, not merged columns" rather than as a completed merge.
- **Kept the four registry-less codex slugs instead of deleting them**, so
  existing session rows don't dangle — but labelled them "unsupported",
  because codex silently falls back to generic metadata and warns "this can
  degrade performance", which is worse than failing loudly.
- **Split effort dispatch into TWO fields** (`ApplyEffort` + `EffortLevels`)
  rather than just fixing the flag form. Levels are per-MODEL: a stale "max"
  from Claude would otherwise reach gpt-5.5 through the CORRECT flag and fail
  with a 400 instead of at argv parse.
- **An unusable effort is dropped with a log, not treated as fatal.** The
  value comes from a persisted session column possibly set long ago against a
  different model; refusing to run would turn a stale setting into an outage.
- **Codex effort is deliberately NOT offered in the web UI yet** — its level
  sets are per-model and the frontend has no source for that table.
  Hardcoding a third copy is what `web/src/effort.ts` exists to prevent.
