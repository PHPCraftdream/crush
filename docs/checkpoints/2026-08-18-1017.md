**CI triage, and a pattern that held.** Two CI failures were root-caused rather
than rerun. `TestReleaseGate_9_DoubleFailureNoDuplicate` (macOS) waited for
`ListPendingRunQueueEntries` to empty, but that query does not see

as a retry loop (`c4c2f17c`). `TestStreamFastExitNoLastLineLoss` (Windows) hit
`bash.exe: fatal error - add_item(...) failed, errno 1`: MSYS could not fork, so
the child never started; the test now re-execs the test binary instead of
spawning a shell (`c14c9b8d`). Neither was a race in production code. That
pattern — "the flake is in the test harness, and it is findable by reading" —
recurred for the rest of the session.

**A tag, and a lesson about what a tag touches.** The operator wanted a
stability marker. `alpha-0.2.0-1` was chosen over `v0.2.0-alpha-1` for three
measured reasons; the third was unexpected. A semver-shaped tag is picked up by
Go's build-info machinery as the main module version, which would have made the
binary report `v0.2.0-alpha-1` in its User-Agent, MCP handshake and web UI while
`crush --version` still said `0.2.0-alpha.0`. Measured in a real clone — a first
attempt via `git worktree` was invalid because Go silently disabled VCS stamping
there, which was only caught because the commit hash vanished from the output.

**The main thread: tool error levels.** Investigating a crashed `crush run` in
`D:\dev\rust\sefer-alloc` (session `t54-e-cards`) found that a todos item with a
bad `status` killed the whole run. The mechanism generalises: in fantasy, a tool
that RETURNS an error sets `isCriticalError` and `executeTools` unwinds the agent
loop, while a tool returning an error RESPONSE feeds the model something it can
correct. In Go the two differ by a reflex-level edit, so the dangerous form had
accumulated across 54 sites. A full audit classified them; a written contract
(`7a6b11c2`) and a guard test (`79cf43e8`) now hold the line, and every site the
test could reach is fixed.

**Process trees.** Reading the tree-kill test's own comment surfaced a
production defect it had explicitly flagged and nobody had filed:
`session.KillProcess` reached no grandchildren on either platform — no group kill
at all on Unix, and on Windows `taskkill /T` walks a parent chain that MSYS
breaks. Fixed with process groups and a Job Object (`68f9c65f`).

## Decisions

- **The criterion is retry-invariance, not "can the model fix it".** Fatal iff no
  input the model could send next and no passage of time would make the call
  succeed. Checkable by reading; the alternative needs a theory of another mind.
- **Default to recoverable under uncertainty**, because the radius is
  asymmetric: a wrongly recoverable error costs one model turn, a wrongly fatal
  one costs the session. Unknown errnos are therefore demoted by default.
- **The guard test was written red on purpose** and committed only once the
  fixes made it green, so no commit leaves the tree broken. That is why #488,
  #490 and #491 share one commit despite the commit-between-tasks instruction.
- **Two `[Job %s] error executing command` sites left untouched** although
  wrongly classified: they are unreachable (mvdan/sh panics rather than return a
  non-nil error with a zero exit code). A behaviourally invisible edit cannot be
  revert-checked, and an unverifiable edit in the agent's main tool is worse than
  the documented mine.
- **`view.go`'s session-ID check was NOT moved**, contradicting the instruction
  given to the agent: `sessionID` is load-bearing on the common path, feeding
  `filetracker.RecordRead`. The lying message was corrected instead.
