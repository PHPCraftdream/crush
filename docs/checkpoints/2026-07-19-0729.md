4. **Diagnosed (on user request) and fixed a real Windows-only bug in
   `internal/shell/exec_windows.go`, found via a completely separate
   investigation** — user asked "why did a `crush run` session in
   `D:\dev\garnet\Apps\IRabi\.crush` hang 15 minutes until timeout?".
   Traced via `crush sessions why`/`last` (in that project's own
   `.crush` dir): the session's last real tool call was `job_kill
   shell_id=01A` at 23:37:23, whose result didn't come back until
   23:53:00 — the internal 15-minute tool watchdog force-cancelled it
   with `ERROR context canceled`. Root-caused by reading the actual
   fork code: `job_kill` → `shell.BackgroundShellManager.Kill()` →
   `shell.cancel()` → `processGroupExecHandler`'s `context.AfterFunc`
   callback on Windows only did `cmd.Process.Signal(os.Kill)` — a
   **single-process** kill. Since `cmd.Stdout`/`Stderr` there are plain
   `io.Writer`s (not `*os.File`), Go's `os/exec` backs them with an OS
   pipe + copy-goroutine that `cmd.Wait()` joins; that goroutine only
   sees EOF once **every** handle-holder closes it. A grandchild the
   killed process had spawned (the IRabi session was mid-diagnosis of a
   Node proxy that likely forked a worker) kept its inherited copy of
   the pipe open, so `cmd.Wait()` — and therefore
   `execCommon`/`runner.Run`, and therefore `bgShell.done` — hung
   indefinitely. Confirmed this is fork-owned code (not IRabi-project
   code) and that the Unix sibling (`exec_unix.go`) already had the
   correct fix (negative-PID process-group signal); Windows never got
   the equivalent. `internal/session.KillProcess` (`taskkill /F /T
   /PID`) was already used for the identical problem class elsewhere
   (cliprovider's PTY kill path, `crush sessions kill`) — confirmed via
   `go list -deps` that `internal/session` has zero dependency (direct
   or transitive) on `internal/shell`, so importing it the other way
   round is safe (no import cycle). Fixed `exec_windows.go` to call
   `session.KillProcess(cmd.Process.Pid)` instead. Wrote a deterministic
   regression test (`internal/shell/exec_windows_test.go`) using a
   self-re-exec helper-process pattern (test binary re-execs itself as
   a "level1" process that forks a "level2" grandchild inheriting
   stdout/stderr without waiting for it, then stays alive until killed
   — avoids brittle dependence on `cmd.exe`/PowerShell handle-
   inheritance quirks). Proved the test has real regression value by
   `git stash`-reverting the fix and re-running: it failed by timeout
   with a goroutine dump showing the exact predicted `io.Copy`/pipe-
   read hang, then passed again (~2s) once the fix was restored.
   Committed as `66bfc158`, pushed, CI green on all three platforms.
