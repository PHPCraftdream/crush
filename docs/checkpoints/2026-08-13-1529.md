**Findings confirmed and fixed (uncommitted, on disk right now):**
- **H2** (P1-1 incomplete): two live `c.cfg.Config().Providers.Get(...)`
  reads remained in `coordinator.go`'s `buildCall` (~line 938) and
  `runInternal` (~line 1003) despite both functions already receiving a
  `pinned *resolvedOverrides` parameter with `.providerCfg` populated from
  the same snapshot. Confirmed genuine — `buildCall` is on the QUEUED
  replacement-call path the file's own comment says pinning matters MORE
  for, and `runInternal`'s live read runs on every single turn (not just
  the rare 401-rebuild path already fixed last round). Fixed: both now
  read `pinned.providerCfg` with the same `providerCfg.ID == ""` zero-value
  sentinel pattern already used at the 401-rebuild site. Builds clean.
- **H3** (P1-3's own tests didn't test what they claimed): the
  `blockingSessionService.PeekInterruptInject` test helper raced `ctx.Done()`
  against the real blocking call in a `select`, meaning the WRAPPER itself
  was context-aware and returned promptly on cancellation regardless of
  whether the fix's `interruptTickOperationTimeout` was present — the tests
  passed identically with the fix reverted. Deeper finding while
  investigating: the production fix (bounding each tick in
  `context.WithTimeout`) is STRUCTURALLY INCAPABLE of protecting against a
  downstream call that truly never checks any context (Go has no
  preemption primitive for that) — what it actually, genuinely delivers is
  bounding a context-AWARE-but-slow dependency to a fixed budget
  independent of the outer (turn-scoped, potentially much longer-lived)
  ctx, which is a real but narrower property than the code
  comments/CHANGELOG claimed. Fixed: rewrote `TestP1_3_TickOperationTimeout`
  to prove the real, narrower property (operation deadline fires on its
  own even though the outer ctx is deliberately never cancelled during the
  assertion window); deleted `TestP1_3_NoUseAfterClose` entirely, since the
  "anti-pattern" it worried about (join completing before the tick's
  operation actually returns) is structurally impossible given
  `handleInterruptTick` is called synchronously within the same goroutine
  whose exit closes `tickerDone` — no separate mechanism exists that could
  "abandon" it early. Corrected the CHANGELOG.md wording for this entry to
  stop overclaiming protection against cancellation-ignoring dependencies.
  **Found and fixed a bug in the orchestrator's OWN rewritten test** during
  verification: the new assertion initially measured elapsed time from
  before the ticker even started, but bounded it against
  `interruptTickOperationTimeout` alone — missing that the first tick
  doesn't fire until `interruptInjectTick` (3s) has already elapsed, so the
  real value clusters at ~13s (3s+10s), right at the edge of a
  `+3s`-margin assertion built assuming a ~10s baseline. Fixed to bound
  against `interruptInjectTick + interruptTickOperationTimeout`; 15/15
  clean under `-race` after the fix (was failing on ~30% of runs before).
- **H4** (a P0-4 test became vacuous): `TestOrphanOutbox_RetryAfterTransientFailure`'s
  fault-injection wrapped the service-level `EnqueueRunQueueEntry`, but
  P0-4's atomic `DrainOrphanOutboxEntry` calls the DB-query-layer
  `qtx.EnqueueRunQueueEntry` internally, never the service method — the
  test's injected failure hasn't fired since #426 merged, so it's been
  passing trivially. Fixed: the mock now wraps `DrainOrphanOutboxEntry`
  directly (the actual call site `processOrphanOutboxEntry` makes), and
  the test/comments were rewritten to describe the property this actually
  demonstrates now (a failed atomic transaction leaves the row exactly as
  it was — still 'pending' — so the next drain tick retries it
  automatically, with no explicit release/retry call needed anymore,
  unlike the pre-#426 claim-based model).
- **M6** (drain context detached from pump shutdown): `processOrphanOutboxEntry`
  built its 10s drain timeout from `context.Background()` instead of
  `p.ctx`, so a slow drain could keep running up to 10s PAST `Stop()`
  being called — well beyond `Stop()`'s own 5s grace period, which would
  then report a forced (non-graceful) shutdown even when nothing was
  actually stuck. Confirmed genuine by reading the code directly. Fixed:
  derives from `p.ctx` (not the caller's already-5s-bound `ctx` parameter
  either, since chaining `context.WithTimeout` off an already-bound parent
  caps the effective deadline at the SHORTER of the two — verified this
  mechanic explicitly before picking `p.ctx` as the right parent).
- **M7** (P1-1 watchdog test margin loosened too far, 50ms → 5s, a 100x
  jump while only ~1s of ceiling-rounding slack was ever justified):
  confirmed the loose bound could no longer distinguish "watchdog
  correctly DB-anchored" from a reintroduction of the exact P0-3 bug for
  any renewal slower than ~4s. Empirically tightened in three steps: 2s
  margin flaked ~5% (2/40 isolated `-race` runs, real scheduling
  contention not a genuine bug); 3s margin is what's currently on disk,
  **verification of its stability is still in progress as of this
  checkpoint** (see Open questions).
