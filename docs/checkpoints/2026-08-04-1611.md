**Round-9 review verdict**: HEAD (`ceac558e`) was NOT a strictly safe step
forward — two BLOCKER-severity regressions, both independently confirmed by
direct code read before fixing (not taken on faith):

1. **BLOCKER-1**: `IsBusy()`/`CancelAll()` still read `activeRequests`
   directly, but the mailbox migration stopped clearing that map's
   plain-sessionID entry on release. Confirmed live: after ANY session's
   first turn, `IsBusy()` returned `true` forever, so `App.Shutdown()`
   (reached by every `crush run` via `defer a.Shutdown()`) always burned
   the full 5-second `CancelAll` drain timeout instead of returning
   immediately. This was a 100%-reproducible regression on every
   already-deployed `crush run` invocation since the earlier deploy at
   `23004ec3`.
2. **BLOCKER-2**: `Run`'s cleanup defer called
   `drainOrRelease`/`drainOrReleaseMerged` unconditionally on every return
   path (not just pre-loop bail-outs, contrary to its own doc comment).
   Two failure shapes: (a) finding something queued left the mailbox
   permanently `mbOwned` with no turn loop left to run it — the session
   wedged busy forever; (b) finding nothing could redundantly re-release a
   DIFFERENT, later owner's session out from under it if a concurrent
   `Run()` had claimed it in the meantime.

Fixed in `c23ef274`:
- BLOCKER-1: migrated `IsBusy`/`CancelAll` to read mailbox state, with a
  filtered fallback for the still-unmigrated `"-summarize"` legacy key.
- BLOCKER-2: added an ownership **epoch** to `mailbox` (bumped only on
  idle→owned transitions). `drainOrRelease` now takes the caller's epoch
  and is a no-op on mismatch. A new `abandonOwnership` method (epoch-aware,
  always ends at idle, logs what it drops) replaces the unconditional
  release in `Run`'s defer specifically — `drainOrRelease` keeps its
  "caller has a live turn loop, may choose to keep running" semantics for
  the loop's own use.
- Two smaller findings from the same review also fixed: `interruptAndReplace`
  gained the same `dispatcherCancel` fallback `Cancel` already had (closing
  a narrow window where an interrupt could report success without actually
  cancelling anything); `drainOrRelease`/`abandonOwnership` stopped zeroing
  `generation.id` on release (only the spent cancel func), since ids are
  meant to stay monotonic per the design doc (needed once #285 wires up
  inject dedup).

## Decisions

- Fixed both BLOCKERs directly and immediately rather than filing +
  continuing the batch — per the user's explicit reprioritization this
  round ("crush не работает"), a live, deployed regression outranks
  backlog work.
- Chose an epoch/ownership-era primitive over simpler alternatives (e.g. a
  boolean "loop entered" flag) after tracing that the real distinction
  needed is "did THIS specific era already end," not "did the loop start" —
  a boolean flag would have broken the legitimate mid-loop early-return
  case that Run's defer is also responsible for releasing.
- Kept `abandonOwnership` as a separate method from `drainOrRelease` rather
  than adding a parameter to change its behavior — they have genuinely
  different contracts (one may choose to keep the era alive, the other
  never does) and conflating them via a flag would have made both harder
  to reason about.
- Did not chase every LOW/INFO finding from the round-9 review in this
  pass (e.g. HIGH-1's "bare Cancel now runs the next queued item instead
  of stopping" — a real UX question requiring a design decision, not a
  quick fix) — filed as future backlog rather than rushed given the two
  BLOCKERs already consumed the round's urgency budget.
