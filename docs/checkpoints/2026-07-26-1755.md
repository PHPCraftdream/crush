**Phase A — orchestrator machinery, discovered broken twice.** Investigated
the previously-landed question-tool (`ask_question`) and worker-role
features and found BOTH were non-functional: (1) `ask_question` was
constructed in `buildTools` but never added to `allToolNames()`, so the
`AllowedTools` filter silently discarded it for every agent — `exit_reason:
"awaiting_answer"` could never fire; (2) the worker sub-agent was
configured read-only (`resolveReadOnlyTools`), so even with the right model
routed to it, it had no edit/write/bash — the whole "smart delegates
hands-on work to a cheap worker" premise was unimplementable. Wrote a full
design doc, `docs/plans/2026-07-26-orchestrator-worker-e2e.md`, covering
both bugs plus the "worker asks orchestrator" round-trip design (proved a
fully synchronous version is impossible — parent LLM is suspended inside
its own tool call while the worker runs — so built "return-and-resume"
instead: a paused worker's question comes back as a normal successful tool
result, answered via a new `resume_session_id` param that continues the
same sub-session).

## Decisions
- `ask_question`/worker-toolset were found NON-functional despite looking
  complete in the prior session's commits — fixed rather than assumed
  working, based on reading `buildTools`'s actual filter logic, not
  commit messages.
- A synchronous worker→orchestrator question is impossible by construction
  (parent LLM suspended inside its own tool call) — built "return-and-
  resume" instead; this reasoning is recorded in the plan doc so it isn't
  re-litigated.
- Orchestrator-mode tool-execution timeout: raised only for orchestrator
  runs via a live closure (`workerSubAgentActive()`), not a blanket bump —
  explicit operator override (`stream_tool_timeout_seconds`) always wins
  in both directions; verified this precedence with dedicated tests.
- Z.AI's `reasoning_effort` is real only for GLM-5.2 per official docs —
  corrected an in-flight sub-agent's design (task #71) that had assumed a
  shared 3-state scheme across all Z.AI models, based on fork code
  behavior rather than the documented API contract.
- Chose `crush models bump` (not `effort`) as the step-up/down command name
  specifically to avoid confusion with the existing `crush models efforts`
  (plural, discoverability-only, task #69).
- npm version stays at 0.1.7 (never tagged/published) rather than bumping
  to 0.1.8 — the CHANGELOG entry was extended, not superseded.
- S2 (worker asks orchestrator) deliberately not smoke-tested live after
  hitting real Z.AI rate-limiting during S1d — relied on task #66's unit
  coverage plus S3's live proof of the same underlying mechanism, a
