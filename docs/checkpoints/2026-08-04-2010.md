**The headline finding: the sub-agent hang was never a mailbox bug.**
Diagnosed from a live repro in `D:\dev\rust\wezterm` (session `split-mux`):
the parent sat in `delegating` with a perfectly fresh heartbeat while its
sub-agent had been stuck on a bare `wc -l <file>` for 41+ minutes. Chain,
established by direct code read:

1. `crush run` auto-approves ONLY the root session id (`app.go`'s
   `AutoApproveSession(sess.ID)`).
2. A sub-agent runs under its OWN child session id
   (`messageID$$toolCallID`, `coordinator.go`'s `CreateAgentToolSessionID`).
3. `permission.Request` looks up `autoApproveSessions[childID]`, misses,
   and falls through to its final `select`, which waits on a UI response
   channel that nothing will ever write to in non-interactive mode.
4. It fires on the first command outside `tools.safeCommands`. `wc` is not
   on that list — which is exactly why the sub-agent's earlier `view` calls
   worked and its first `bash` did not.

Proof it was an oversight rather than a design choice:
`agentic_fetch_tool.go` already passes a `SessionSetup` that calls
`AutoApproveSession` on its child. The MAIN delegation path passed no
`SessionSetup` at all, so it never got the same treatment. Fixed by
inheritance (`InheritSessionAutoApprove`), deliberately not a blanket
grant — an interactive parent's sub-agent must still prompt, and
`--restrict-run` still gates on top.

This also retro-invalidates earlier diagnoses: the shamir-db `find` hang
and probably other "stuck tool" sightings were most likely this same bug,
not the tool-timeout class they were filed under (#273 re-scoped
accordingly).

**Release-review blockers, all fixed and committed this round:**
- **P0-A** (`db546653`) — a late interrupt's replacement was only ever
  read by the cancel path; when the cancel lost the race to Stream's own
  completion, the normal final drain released the session without seeing
  it. `drainOrReleaseFinal` now evaluates replacement → submitted →
  legacy → release as one atomic operation.
- **P0-B** (`1410b398`) — `InterruptAndSend`/`requeueInterruptMessage` on
  an idle session queued into the legacy queue with no runner while the
  web client was told "queued". They now start a detached run, which is
  what the mailbox's own contract already specified for the "no owner"
  answer.
- **P0-C** (`54fac263`) — `CancelAll` used the ordinary per-generation
  `Cancel`, so the cancel-handling branch immediately drained and started
  turn N+1 on an uncancelled `runCtx`; `App.Shutdown` then tore the DB
  down under a live agent. Added a one-way `stopped` latch +
  `hardStop()`; `CancelAll` latches every mailbox FIRST, then cancels
  both generation and dispatcher. Queued work is left in place, not
  discarded.
- **P0-D** (`bd90f915`) — the sub-agent permission hang above.
- **P1-B** (`d76b5eba`) — `runTurn`'s bare `defer wg.Wait()` on the title
  goroutine was only as bounded as the goroutine itself. Replaced with a
  done-channel + `titleJoinGrace` select; an overrunning title is
  detached (it still persists via its `WithoutCancel` rename).

**Timer-driven activity, removed everywhere (`55eb2fc5`)** — the user's
explicit direction ("убрать все таймерные тикеры, только фактическая
активность"). `stream_watchdog.go` called `recordActivity()` every tick
while any tool was open, so the heartbeat meant "a tool call is OPEN",
not "something is happening" — the source of the 38-minute false-alive
reading. Removing it turned out to be safe without regressing task #222's
concern: `withActivityNotify` already composes each session's activity
callback with its ancestors', so a delegated sub-agent's REAL stream
callbacks propagate up and keep every ancestor's heartbeat fresh. The
#222 test that pinned the old behaviour was replaced by one asserting the
inverse. `sessions watch` got the display half: real message live-tail of
every descendant in the call tree, breadth-first, instead of a
once-per-second synthetic pulse whose "only print when changed" throttle
never fired (the note embedded a live-updating age).

**Deployed** — `55eb2fc5` is installed and verified via `crush --version`.
This matters more than usual: the user had been running a binary from
before ANY of rounds 9-13, so several of the symptoms they were reporting
were already-fixed-but-not-shipped.
