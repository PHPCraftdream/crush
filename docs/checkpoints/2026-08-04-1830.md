**Round-11 review verdict**: unlike rounds 9 and 10, this round found NO

the OS session lock / cancel lifecycle instead — precisely where the
still-incomplete stage-2 migration (#281/#284/#285 still pending) leaves
invariants owned by neither structure:

1. **HIGH-1**: `runTurn`'s end-of-turn drain flipped the mailbox to
   `mbIdle` synchronously in its body — strictly before `runTurn`'s own
   `defer wg.Wait()` (title generation, up to several seconds on a
   cancelled-context DB-rename fallback) unwound, and well before `Run`'s
   own `defer lk.Release()` fired (only once `Run()` itself returns).
   `IsSessionBusy()==false` was observable in-process while the OS-level
   session lock was still actually held — a same-process concurrent
   `Run()` call for the identical session could become the new in-process
   owner and then fail OS-lock acquisition with "already in use" from its
   own process's not-yet-unwound prior turn, with the message silently
   dropped (that error path never re-queues). This meant P0-3 (closed in
   rounds 9/10) wasn't actually fully closed in the production
   configuration (`dataDir != ""`) — a concurrent send in the final-drain
   window still failed, just loudly instead of silently.
2. **MEDIUM-1**: the legacy-queue reclaim path called the historical
   `reclaimSameEra` with a literal `nil` `dispatcherCancel` and never
   touched `mb.current.cancel`, which still held the just-finished turn's
   own spent (but non-nil) cancel func. `Cancel()`'s and
   `InterruptAndReplace()`'s shared fallback is gated on
   `current.cancel == nil`, so it never reached the working fallback:
   `Cancel()` silently no-opped, and `InterruptAndReplace()` reported
   success while cancelling nothing.

Both independently confirmed via direct code read before delegating a
fix (not just taking the reviewer's word) — same zero-trust discipline as
every prior round.

**Fixed in `8ba3d3f8`**: `mailbox.reclaimSameEra` replaced with
`mailbox.drainOrReleaseFinal`, which unifies the mailbox's own submitted-
queue check, the legacy `messageQueue` check, and the OS lock release into
ONE atomic operation holding `mb.mu` for its entire body — release only
happens (still under `mb.mu`) after BOTH sources are confirmed empty,
immediately before the state flip to idle, so no same-process observer can
ever see "not busy" before the OS lock is genuinely free. A legacy-queue
hit keeps the OS lock held for the reclaimed turn rather than
releasing-then-reacquiring (which would open a real cross-process race).
For MEDIUM-1, `Run`'s whole-call `runCancel` is now threaded down through
`runTurn` into `drainOrReleaseFinal`, and both `mb.dispatcherCancel` and
`mb.current.cancel` are set correctly, atomically, in the same reclaim
branch — a first draft that set only `dispatcherCancel` still failed a
real test, since `current.cancel` being non-nil meant the fallback was
never reached.
