**Дата:** 2026-07-31
**Инцидент:** сессия `task-276` в `D:\dev\rust\wezterm`, PID 39132
**Статус:** главная причина устранена; корневая причина общего блока — **не доказана** (улика потеряна, см. §6)

## 2. Найденная и устранённая причина: вотчдог не мог сработать

### 2.1 Суть

В `internal/agent/stream_watchdog.go` цикл тика выглядел так:

```go
if toolsInFlight.Load() > 0 {
    if toolMaxDuration > 0 && exemptToolsInFlight.Load() == 0 {
        // ...единственная ветка, способная выстрелить...
    }
    last.Store(now.UnixNano())
    continue        // пропускает idle, absoluteDeadline И hardDeadline
}
```

Когда в полёте есть **exempt**-вызов (делегирование саб-агенту через
`agent`-tool):

1. проверка кэпа `toolMaxDuration` пропускается целиком;
2. `last.Store(now)` на каждом тике непрерывно сбрасывает idle-таймер;
3. `continue` пропускает все остальные дедлайны, включая hard cap.

**Итог: пока делегирование в полёте, родительский вотчдог не мог сработать
ни по одному условию. Ожидание родителя было неограниченным по построению.**

Ровно этот сценарий и завис: четыре `agent`-вызова в полёте → у родителя
нулевая защита → зависший ребёнок морозит родителя навсегда, без ошибки,
без finish-части, без диагностики.

### 2.2 Происхождение

Это **регрессия, внесённая мной же** в этой сессии, коммит `9226cb9a`
(«exempt sub-agent delegations from the stream watchdog's toolMaxDuration
cap»). Исходная проблема была реальной: родитель убивал здоровые
делегирования тем же 15-минутным кэпом, что предназначен для одиночного
`bash`. Но лечение было неверным по форме — вместо **большего** предела я
убрал предел **вообще**.

Причём код рядом прямо декларировал нарушенный инвариант — комментарий к
`orchestratorToolExecutionMaxDefault`:

> Still bounded (not infinite) so a genuinely wedged sub-agent eventually
> gets force-cancelled instead of hanging the parent turn forever.

### 2.3 Исправление

- `startStreamWatchdog` принимает отдельный `exemptToolMaxDuration`; для
  каждого батча выбирается `activeCap` (exempt → щедрый предел, иначе —
  обычный). Предел **всегда конечен**.
- Явно заданный `hardCap` (> 0) теперь соблюдается и во время исполнения
  инструментов — «hard» должен означать hard. `absoluteDeadline`
  намеренно не применяется здесь: это idle-дедлайн, и долгий, но здоровый
  инструмент не должен об него спотыкаться.
- `agent.go`: новый `effectiveExemptToolMaxDuration()` — по умолчанию
  `orchestratorToolExecutionMaxDefault` (45 мин), явный операторский
  `Options.StreamToolTimeoutSeconds` перекрывает.

Важная деталь: новый предел привязан к **факту наличия `agent`-вызова в
полёте**, а не к тому, настроена ли Worker-модель. Старое правило
(`workerSubAgentActive`) давало 45 минут только при настроенном Worker'е — а
без него делегирование падало обратно на 15-минутный кэп для примитивных
инструментов. Именно это и порождало исходные ложные срабатывания.

**Тест:** `TestStreamWatchdog_ExemptToolUsesLargerCapNotNoCap` закрепляет обе
половины контракта — не стрелять до `exemptCap` и **обязательно** выстрелить
после. Sanity-проверен откатом к старому поведению: тест падает ровно на
нужном утверждении.

## 3. Почему инцидент оказалось невозможно диагностировать

При живом зависшем процессе не удалось получить **ни одного** стека:

| Механизм | Почему не сработал |
|---|---|
| pprof | Скомпилирован в бинарник (`main.go` импортирует `net/http/pprof`), но слушает только при выставленном `CRUSH_PROFILE`. Включить постфактум на уже запущенном процессе нельзя. |
| delve attach | Продакшн-сборка идёт с `-s -w` (стрип DWARF) → `could not find goroutine array`. |
| detach после attach | `quit -c` потребовал `--accept-multiclient`; без него delve **убил** процесс на выходе. |

Итог: единственный живой экземпляр бага был уничтожен самой попыткой его
изучить. Это делает любое зависание в бою принципиально неисследуемым.

### Исправление

Добавлен `internal/log/goroutine_dump.go` → `DumpGoroutines(reason)`:
пишет стеки **всех** горутин в `goroutines-<pid>-<ts>.txt` рядом с
`crush.log`. `runtime.Stack` не требует ни символов, ни открытого порта, ни
действий оператора — работает в стрипнутых release-сборках.

Вызывается из `onFire` стрим-вотчдога: срабатывание вотчдога **и есть**
зависание, пойманное в единственный момент, когда улика ещё существует.

## 4. Ложный сигнал живости

`crush sessions why` и `sessions list` показывали `status: running`,
`heartbeat 4s old` для процесса, который 15+ минут не делал ничего.

Причина: heartbeat (`internal/session/lock.go`) — это отдельная горутина,
раз в 10 с делающая `os.Chtimes` по lock-файлу. Она не разделяет ничего с
рабочими путями агента, поэтому продолжает тикать, даже когда все остальные
горутины процесса заблокированы.

**«alive» означает «процесс существует», а не «сессия движется»** — то есть
ровно противоположный сигнал тому, что нужен оператору, решающему, ждать
или убивать.

Заведено как задача #192 (не исправлено в этом заходе). Направление: либо
двигать heartbeat от реального прогресса хода (те же сигналы, что видит
`bump()` вотчдога), либо в `sessions why`/`list` сверять свежесть heartbeat
с временем последней активности сообщений и показывать отдельное состояние
«жив, но без прогресса N минут».

дереве.

## 6. Что осталось недоказанным

**Фикс §2 гарантирует, что родитель больше не может ждать вечно.** Но он не
объясняет, что именно заблокировало все пять агентов одновременно —
родителя и всех четырёх детей. У каждого ребёнка свой вотчдог; тот факт,
что не выстрелил ни один, указывает на **общий для процесса ресурс**, а не
на провайдера.

Главный подозреваемый — единственное writer-соединение с БД:

```go
// internal/db/connect.go
conn.SetMaxOpenConns(1)
```

Это осознанное решение (защита от рассинхрона WAL → `SQLITE_NOTADB`), но оно
означает, что **весь процесс делит одно соединение**. Пять конкурентных
агентов пишут сообщения непрерывно; любой держатель этого соединения,
заблокировавшийся на чём-либо, замораживает всех разом. Косвенное
подтверждение — ошибка из инцидента 30.07:

```
"Failed to update parent session cost" error="begin transaction: context deadline exceeded"
```

то есть код не смог даже **начать** транзакцию, не получив соединение в
отведённый дедлайн — прямое свидетельство острой конкуренции за него при
конкурентных саб-агентах.

Проверено и **исключено** как причина:

- транзакции в `internal/session/session.go` (`DrainPendingInjects`,
  `ConsumeInterruptInject` и др.) корректно ограничены: `defer rows.Close()`,
  `defer tx.Rollback()`, коммит в конце, без медленной работы внутри;
- sqlc-генерируемый код материализует строки в срез до возврата, поэтому
  классического дедлока «открытые `Rows` + вложенный запрос при
  `MaxOpenConns(1)`» в этих путях нет;
- `flushCtx` в error-путях `agent.go` — `context.WithoutCancel` + 15 с,
  ограничен.

Не проверено (следующий шаг): пути, удерживающие соединение во время
сетевого ожидания или блокировки на мьютексе; предупреждения предыдущего
ревью (`docs/reviews/2026-07-30-project-review.md`) про «опасные глобальные
сериализаторы и lock convoy» и «не удерживать permission mutex во время
ожидания пользователя».

**Теперь это расследуемо**: при следующем повторении вотчдог выстрелит по
конечному пределу и автоматически сохранит дамп всех горутин рядом с
`crush.log` — то есть даст ровно ту улику, которой не хватило сейчас.
